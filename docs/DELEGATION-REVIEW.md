# Independent review: HeavenKey delegation v1

The reviewed delegation profile has no recorded blocking source findings. Local checks passed 45 Rust tests, 75 reference checks and 138 virtual browser cases. [Review evidence](evidence/v05-independent-review.json) and [package sources](evidence/v05-donor-research.json) record the detailed checks.

## Standards and donor decision

UCAN describes delegated authority that stays the same or becomes narrower, with validity bounds checked when authority is exercised. Its issuer and audience are DID principals, and the issuer's associated private key signs the token. HeavenKey adopts attenuation and explicit chain linkage as principles. Its service signs every link and its stable account aliases are not signing keys, so its binary message, envelope and identifiers are a separate local profile. [UCAN overview](https://github.com/ucan-wg/spec/tree/a73ee55ec82a90004227034873095e080d0df619), [delegation specification](https://github.com/ucan-wg/delegation/tree/1cb32dbc9d4d15a23bf9844a02515d760b81e816).

Revocation invalidates a proof path and descendants that depend on it. A separate unrevoked path may still provide the same capability. HeavenKey consults the current database while resolving the full chain; signatures alone cannot establish current revocation state. Ancestor revocation blocks descendant use and further delegation, including a ceremony or approval started before revocation. [UCAN revocation specification](https://github.com/ucan-wg/revocation/tree/1235679bef2d74b7be46a6295e40184936247649).

The selected crypto donor is the installed `ed25519-dalek =2.2.0`, BSD-3-Clause. Its exact crate source is `8016d6d9b9cdbaa681f24147e0b9377cc8cef934`; the pinned [manifest](https://github.com/dalek-cryptography/curve25519-dalek/blob/8016d6d9b9cdbaa681f24147e0b9377cc8cef934/ed25519-dalek/Cargo.toml) and [license](https://github.com/dalek-cryptography/curve25519-dalek/blob/8016d6d9b9cdbaa681f24147e0b9377cc8cef934/ed25519-dalek/LICENSE) were checked. Reuse strict verification and the existing lockfile; no custom curve/signature primitive or new runtime dependency is required. [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032.html) supplies the algorithm reference and public vectors; its illustrative algorithm code is not copied into production. The [library's strict-verification documentation](https://docs.rs/ed25519-dalek/2.2.0/ed25519_dalek/struct.VerifyingKey.html#method.verify_strict) defines its additional rejection policy.

## Reviewed behavior

The Rust parser rejects unknown, missing and duplicate fields, duplicate or empty actions, malformed byte arrays, unknown profiles and out-of-range values. Nullable parent/delegator fields remain required. It bounds ASCII resource length, safe integer times, depth, budget and input size. The domain-separated binary encoder signs semantic fields; identifiers hash that message plus the signature. The independent Node/Bun standard-crypto encoder agrees on public synthetic vectors and actual API-generated signatures and identifiers.

Every link retains the trusted service issuer, exact parent identifier, parent-holder delegator, unchanged resource, subset actions, narrower time bounds and decreasing budget. Complete chains are checked for signatures, cycles, current time and ancestor revocation. Stored identifiers, parent pointers and account metadata must match signed fields. Leaf authority matches the authenticated account and invocation. Listings show inactive records with status without granting execution rights; authorized idempotent revocation remains separate from active invocation.

Root creation is owner-only. Delegation belongs to the current parent holder; revocation belongs to the owner or actual issuing account. All three writes use exact-action, session/account/key-bound, single-use approval, with permission and chain rechecks at start, finish and mutation. The existing monotonic 60-second expiry and cap of 128 approvals remain. Invocation binds exact fields and its distinct purpose to a fresh passkey ceremony, rechecks current authority and records execution once under the service mutex and SQLite transaction. Existing write gates, counters, account alias, tombstones and account-wide session cleanup remain intact.

The UI shows action, recipient, parent, TTL and budget before confirmation, snapshots inputs once and renders values with `textContent`. The browser bundle retains the pinned SDK's MIT notice and uses same-origin API requests. An independent case-name comparison with commit `5de017d8b1a8eb46ca416ed92eed9e442e9350e3` confirms all 96 earlier browser cases remain, 42 were added and 0 were removed, including the prior cancellation/retry checks.

## Proof boundary

The 75 reference checks cover 32 fixtures, 35 chain scenarios, 7 raw JSON denial cases and 1 ordering/whitespace identity check. Those raw cases include escaped duplicate keys, unknown/missing fields, signature length and size. General parser equivalence is not proved: JavaScript `JSON.parse` normalizes numeric spellings, while Rust's typed integer decoder is stricter. Rust also has separate required-nullable and byte-length tests. The public repeated-byte seed is deliberate synthetic test data; the production service key is absent from the vectors.

This is a local service-mediated profile. Real hardware, trusted authenticator transaction display, hosted Ubuntu execution, UCAN/DID interoperability, holder-signed offline use and distributed concurrency remain unverified.
