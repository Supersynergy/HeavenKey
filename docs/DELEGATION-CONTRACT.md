# HeavenKey delegation v1 contract

Version0.5 adds a service-attested, passkey-approved delegation profile beside the unchanged legacy grant format. The service holds the existing issuer Ed25519 key and signs every link. Delegator/audience identifiers are stable account aliases, not Ed25519 keys. A fresh verified passkey authorizes each online write. This is not UCAN, a DID profile, a holder-signed offline token or trusted hardware transaction display. No new dependencies, user private keys or service are required.

## Profile and signing bytes

Add crates/verifier/src/delegation.rs and export it from lib.rs; preserve legacy24 verifier tests and signing bytes. Public v1 body uses strict serde with exactly these fields:

- profile: literal "heavenkey-delegation-v1"
- issuer:[u8;32], delegator:Option<[u8;32]>, audience:[u8;32]
- resource:String, actions:BTreeSet<Action>
- not_before:u64, expires_at:u64
- remaining_delegations:u8, parent:Option<[u8;32]>, nonce:[u8;16]

Envelope is existing Signed<DelegationGrant>:{body,signature:[64 byte integers]}. Reject unknown/missing/duplicate fields, invalid byte lengths, duplicate/empty/unknown actions and unknown profile. JSON property order and whitespace do not affect signature semantics. Resource is1..256 printable ASCII bytes (0x21..0x7e). Times must be integers <=9007199254740991; not_before<expires_at. remaining_delegations<=4. Maximum5 links and4096 JSON bytes per signed link; API body limit32KB retained. Reject identical audience/delegator and repeated audiences within a chain to avoid cycles.

Deterministic signing message: UTF-8 bytes "HEAVENKEY-DELEGATION-v1" followed by NUL, then issuer32, delegator tag(0 absent,1 present) and optional32 bytes, audience32, resource byte length u16 big-endian then ASCII resource bytes, action bitmask u8(Read1,Write2,Unlock4), not_before u64 big-endian, expires_at u64 big-endian, remaining_delegations u8, parent tag(0 absent,1 present) and optional32 bytes, nonce16. Profile is checked against the literal before message creation; the domain fixes its version. Ed25519 signing/strict verification reuse installed ed25519-dalek. Identifier SHA256(message || signature64). Never hash incidental JSON formatting.

Chain verification checks every signature against the trusted service root; every issuer must equal that root. Root has parent=null and delegator=null. Child parent is exact previous identifier, delegator equals parent audience, resource identical, actions nonempty subset, not_before>=parent.not_before, expires_at<=parent.expires_at, parent budget>0 and child budget<parent budget. Check all links for validity at now and membership in supplied current revoked-ID set. Leaf audience must equal verified account alias; resource and requested action must match. Wrong order, missing/extra root, unknown profile, bad signature, excessive depth/budget/size, cycles, time and authority escalation fail closed. Library exports idiomatic sign/id/verify-chain/message helpers for API and vector tests. Inputs never bypass validation simply because signatures are service-generated.

## API alongside legacy routes

Use a separate SQLite delegations table(id PK,parent_id nullable FK,recipient_id user FK,delegator_id user FK,token TEXT,revoked BOOLEAN). Root delegator_id is the issuing owner; child is the verified parent holder. Preserve legacy users/grants/operations/credentials/migration unchanged and idempotent. Resolve full chain by following stored parent IDs, max5, detect cycle/unknown row; compare token IDs and parent pointers, reverify signatures/current ancestor revocation. Trust no client chain or database token merely by presence. Revocation is inherited at read/delegate/invoke; direct tombstones persist and descendants cannot bypass by replacing parent. No unbounded recursion.

Strict management variants and writes:

- delegation_create:{guest_name,ttl_seconds,remaining_delegations}; POST /api/delegations same fields plus approval_id. Owner only; TTL1..3600,budget0..4; fixed lab resource Read; random nonce16. Response {id,grant,chain}.
- delegation_delegate:{parent_id,guest_name,ttl_seconds,remaining_delegations}; POST /api/delegations/delegate same fields plus approval_id. Session account must be current parent audience, parent chain valid and unrevoked. TTL1..3600,expiry now+TTL<=parent expiry,budget<parent budget; retain Read and fixed resource. Recipient exists and must not be any existing chain audience. Response {id,grant,chain}.
- delegation_revoke:{id}; POST /api/delegations/revoke:{id,approval_id}. Owner can revoke any; original delegator_id can revoke its own issued child. Parent holder cannot revoke unrelated children. Require fresh exact-action approval; return {revoked:true}. Idempotent only for same authorized existing grant.

Every write reuses existing 60s/one-use/session/account/actual-active-key approvals, including failure consumption and128 cap. Existing four mutations stay gated. Check permissions/current chain at management start/finish and again at mutation. Never mint a child or revoke on mere bearer possession. All processing uses existing Inner mutex and transaction patterns; single-process proof only.

GET /api/delegations returns {profile:"heavenkey-delegation-v1",max_chain:5,grants:[...]}. Each row includes id,guest,grant,chain,parent_id,revoked(direct),effective_revoked(any ancestor),can_delegate(current holder and active chain,budget>0),can_revoke(owner or actual issuer account). Owner sees all; others see received grants or personally issued descendants, not unrelated users' grants. Listing expired/revoked records is allowed with status; it never grants execution rights.

Add optional delegation_invocation to /api/auth/start and /finish:{id,resource,action,arguments}. It is mutually exclusive with legacy invocation and management; generic login remains unchanged. Bind exact request fields and ID to the fresh WebAuthn ceremony. Resolve and verify full current DB chain against verified passkey account at start and finish. Finish executes once through separate delegation_operations table(id PK,delegation_id FK,holder FK,created), rechecking authority before atomic record. Preserve verified key/counter handling, source guards and legacy invocation responses. Delegated invocation response uses existing {allowed:true,...} convention. Approval and invocation tokens remain memory-only; revoking credentials retains all0.4 session/ceremony cleanup.
