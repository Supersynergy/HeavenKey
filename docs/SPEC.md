# HeavenKey access lab

Owner enrollment requires a 256-bit, operator-only bootstrap token generated by the server and a verified WebAuthn registration. Guests may enroll first without acquiring ownership. The reserved owner name requires the token. Only one successful owner enrollment is permitted; pending competing enrollments are rejected after consumption, including after restart. Legacy spike data is not retroactively trusted. The UI clears the token after successful enrollment. The token never appears in API responses or runtime logs.

The browser creates and uses WebAuthn credentials through real navigator.credentials APIs. The authenticator is an isolated virtual CTAP2 device. Rust verifies the signatures through webauthn-rs. A signed access grant is bound to the enrolled guest credential. A server-side, single-use WebAuthn challenge is paired with the exact invocation. SQLite stores credentials, revocations and accepted operations. Challenges stay server-side and expire; process restart invalidates outstanding challenges.

Tests: owner and guest enrollment, read grant creation, guest invocation, changed action/resource/arguments, wrong origin/RP/challenge/signature/user-verification, replay, foreign holder, expired/revoked grant, restart and duplicate registration. Live hardware is deferred by the user.

Private keys created for the local issuer stay under data/. No production accounts, funds or physical actuators are involved. The spike uses its own versioned grant profile, not a claim of UCAN interoperability.
