# HeavenKey access lab

Owner enrollment requires a 256-bit, operator-only bootstrap token generated by the server and a verified WebAuthn registration. Guests may enroll first without acquiring ownership. The reserved owner name requires the token. Only one successful owner enrollment is permitted; pending competing enrollments are rejected after consumption, including after restart. Legacy spike data is not retroactively trusted. The UI clears the token after successful enrollment. The token never appears in API responses or runtime logs.

The browser creates and uses WebAuthn credentials through real navigator.credentials APIs, with @simplewebauthn/browser 14.0.0 as its ceremony adapter. Tests use isolated virtual CTAP2 devices; Rust verifies signatures through webauthn-rs. The grant's original credential-derived audience remains a stable server-resolved account alias. Any active credential of that account may invoke it. Removing a credential prevents that key from authenticating but does not revoke account grants; grant revocation is separate. This contract is not an offline or interoperable DID profile.

Accounts may have eight active credentials. Addition binds the exact initiating session, account and active authorizing key. Initial registration and credential addition have separate ceremony purposes. Authentication reloads the used credential's active state and counter before accepting. Removal preserves a tombstone, refuses the last active key and invalidates all account sessions, approvals and pending authentication/enrollment. Idempotent legacy migration preserves the initial alias and counters without reactivating tombstones.

All four sensitive writes require a fresh, user-verified passkey approval: credential addition/removal and grant issuance/revocation. Management assertions reuse the authentication endpoints with a strict typed purpose, mutually exclusive with invocation. Start and finish require the same valid session and matching account; owner-only purposes check the current role. Finish creates an approval without a new login session or mutation. The mutation consumes it once, even on a parsed failed attempt. It binds exact parameters, session, account and the active signing key. In-memory approvals use a monotonic 60-second lifetime, are capped at128 and disappear on restart. The detailed contract is STEPUP-CONTRACT.md.

The browser displays action and target before requesting confirmation, retains tokens only in memory and permits cancel/retry. Server challenge binding does not provide a trusted authenticator display of transaction data; a compromised browser remains outside this proof.

A server-side, single-use WebAuthn challenge is paired with the exact invocation. SQLite stores credentials, revocations and accepted operations. Challenges stay server-side and expire; process restart invalidates outstanding challenges.

Tests cover owner and guest enrollment, grants, guest invocation, changed action/resource/arguments, wrong origin/RP/challenge/signature/user-verification, replay, foreign holder, expiry, revocation and restart. The96-case browser suite retains all69 prior cases and adds four token-only write denials, exact approval parameters/session/account/kind, duplicate execution and actual passkey abort/retry. Approval expiry is tested with monotonic unit data, without waiting60seconds or adding a runtime test-clock override. Live hardware is deferred by the user.

Private keys created for the local issuer stay under data/. No production accounts, funds or physical actuators are involved. The spike uses its own versioned grant profile, not a claim of UCAN interoperability.
